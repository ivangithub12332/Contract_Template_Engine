# Презентация проекта: Шаблонизатор договоров

Этот файл можно использовать как основу для PowerPoint / Google Slides.  
Каждый раздел `Слайд N` — отдельный слайд.  
Блок `Что сказать` — текст для докладчика.

## Слайд 1. Название проекта

**Шаблонизатор договоров**

Система для загрузки шаблонов договоров, настройки переменных и генерации готовых документов.

Команда:

- backend;
- frontend;
- аналитика;
- тестирование;
- проектное управление.

**Что сказать**

Наш проект решает задачу автоматизации подготовки договоров. Вместо ручного редактирования каждого документа пользователь выбирает шаблон, заполняет форму и получает готовый файл.

## Слайд 2. Проблема

При ручной подготовке договоров возникают типовые проблемы:

- много повторяющегося текста;
- высокий риск ошибок при копировании данных;
- сложно контролировать актуальность шаблонов;
- неудобно переиспользовать уже заполненные значения;
- нет единой истории созданных документов.

**Что сказать**

Основная проблема — договоры часто создаются по одним и тем же заготовкам, но данные каждый раз подставляются вручную. Это долго, неудобно и повышает риск ошибок.

## Слайд 3. Цель проекта

Цель — создать веб-сервис, который позволяет:

- загружать шаблоны договоров;
- автоматически находить переменные в шаблоне;
- настраивать поля формы;
- создавать документы по заполненным данным;
- хранить историю созданных документов;
- управлять доступом через роли.

**Что сказать**

Мы сделали не просто форму, а полный цикл: от загрузки шаблона до генерации и скачивания готового документа.

## Слайд 4. Роли пользователей

В системе три роли:

| Роль | Возможности |
| --- | --- |
| `user` | создаёт документы по опубликованным шаблонам, видит свою историю |
| `methodologist` | загружает шаблоны, настраивает переменные, публикует шаблоны |
| `admin` | управляет шаблонами и ролями пользователей |

**Что сказать**

Роли нужны, чтобы обычный пользователь не мог случайно менять шаблоны или роли. Настройкой шаблонов занимается методолог, а администратор управляет системой.

## Слайд 5. Основной пользовательский сценарий

1. Методолог загружает шаблон `docx` или `pdf`.
2. Система распознаёт переменные.
3. Методолог настраивает поля.
4. Шаблон публикуется.
5. Пользователь выбирает опубликованный шаблон.
6. Пользователь заполняет форму.
7. Система генерирует документ.
8. Документ сохраняется в истории.

**Что сказать**

Главный сценарий построен вокруг разделения обязанностей: один человек готовит шаблон, другой использует его для создания документов.

## Слайд 6. Архитектура проекта

Проект состоит из двух частей:

- **Backend:** Laravel + PostgreSQL + Docker.
- **Frontend:** React + TypeScript + Vite.

Связь между frontend и backend:

```text
React frontend -> REST API -> Laravel backend -> PostgreSQL / storage
```

**Что сказать**

Frontend отвечает за интерфейс, backend — за авторизацию, хранение данных, работу с файлами, генерацию документов и API.

## Слайд 7. Backend

Backend реализует:

- REST API;
- регистрацию и вход;
- Laravel Sanctum token-auth;
- роли пользователей;
- загрузку шаблонов;
- распознавание переменных;
- создание документов;
- историю документов;
- скачивание файлов;
- Swagger-документацию.

**Что сказать**

Backend закрывает всю бизнес-логику. Frontend не генерирует документы самостоятельно, он отправляет данные на API.

## Слайд 8. Frontend

Frontend реализует:

- экран входа и регистрации;
- каталог шаблонов;
- фильтры по шаблонам;
- загрузку шаблона;
- настройку переменных;
- создание документа;
- предпросмотр данных;
- историю документов;
- повторное создание документа;
- управление пользователями для администратора.

**Что сказать**

Интерфейс сделан как рабочее приложение, а не как демонстрационная страница. Все основные действия доступны из бокового меню.

## Слайд 9. Работа с шаблонами

Поддерживаются форматы:

- `docx`;
- `pdf`.

Для `docx` используются плейсхолдеры:

```text
{{client_name}}
{{contract_date}}
{{total_amount}}
```

Для `pdf` используются поля формы AcroForm.

**Что сказать**

Для Word-документов переменные задаются через двойные фигурные скобки. После загрузки система находит эти ключи и создаёт по ним поля формы.

## Слайд 10. Типы переменных

Поддержанные типы:

- текст;
- многострочный текст;
- число;
- сумма;
- дата;
- выбор из списка;
- логический признак;
- таблица / повторяющийся блок.

**Что сказать**

Тип переменной влияет на то, какое поле пользователь увидит в форме и как будет валидироваться введённое значение.

## Слайд 11. Генерация документа

Процесс:

1. Пользователь выбирает шаблон.
2. Заполняет форму.
3. Открывает предпросмотр.
4. Нажимает `Сгенерировать документ`.
5. Получает файл.
6. Документ появляется в истории.

Поддерживается скачивание:

- исходного формата;
- PDF для DOCX-документа.

**Что сказать**

Пользователь не работает напрямую с файлом шаблона. Он работает с формой, а система сама подставляет значения и отдаёт готовый результат.

## Слайд 12. История документов

История позволяет:

- видеть созданные документы;
- скачивать документы повторно;
- скачать PDF-версию;
- открыть документ повторно с прежними значениями;
- создать новый документ на основе старого.

**Что сказать**

История нужна, чтобы документы не терялись, а уже введённые значения можно было использовать повторно.

## Слайд 13. Управление пользователями

Для администратора доступен раздел `Пользователи`.

Возможности:

- посмотреть список пользователей;
- найти пользователя;
- отфильтровать по роли;
- изменить роль пользователя.

**Что сказать**

Первого администратора нужно назначить вручную через команду, а дальше роли можно менять уже через интерфейс.

## Слайд 15. Хранение данных

## Возможные вопросы и ответы

### Почему нужны роли?

Чтобы разделить доступ. Обычный пользователь создаёт документы, методолог готовит шаблоны, администратор управляет пользователями и удалением.

### Где хранятся документы?

Метаданные хранятся в PostgreSQL, файлы — в Laravel storage.

### Почему первый администратор назначается вручную?

Потому что после регистрации все пользователи получают безопасную роль `user`. Первого администратора нужно назначить вручную, дальше роли меняются через интерфейс.

### Можно ли скачать документ в PDF?

Да. Для DOCX-документов поддерживается скачивание PDF-версии.

### Что будет, если шаблон не опубликован?

Обычный пользователь не сможет создать по нему документ. Сначала методолог или администратор должен настроить и опубликовать шаблон.

### Можно ли переиспользовать старые значения?

Да. В истории есть действие `Повторить`, которое открывает форму с прежними значениями.

### Что хранится в GitHub?

Только код и документация. Локальные шаблоны, документы, пользователи и база в GitHub не попадают.

### Зачем нужна ветка `full-project`?

Это общая интеграционная ветка, где лежат backend, frontend и общая инструкция.

### Зачем нужна ветка `frontend`?

Это чистая ветка только с frontend-файлами, без backend-кода.

## Мини-речь на защиту

Здравствуйте. Мы представляем проект "Шаблонизатор договоров".  
Цель проекта — автоматизировать создание договоров по заранее подготовленным шаблонам.

В системе есть три роли: обычный пользователь, шаблонизатор и администратор. Шаблонизатор загружает DOCX или PDF-шаблон, система распознаёт переменные, после чего эти переменные можно настроить: задать подпись, тип, обязательность, подсказку и значение по умолчанию. Когда шаблон готов, он публикуется.

Обычный пользователь выбирает опубликованный шаблон, заполняет форму и получает готовый документ. Документ сохраняется в истории, его можно скачать повторно или создать новый документ на основе старых значений.

Backend реализован на Laravel, использует PostgreSQL, Docker и Laravel Sanctum для авторизации. Frontend реализован на React, TypeScript и Vite. API задокументирован через Swagger.

Проект закрывает полный цикл работы с шаблонами: загрузка, распознавание, настройка, публикация, генерация документа и история.
